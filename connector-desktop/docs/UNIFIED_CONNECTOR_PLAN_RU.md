# Единый Structura Connector: ядро, доступ, интерфейс и обработка моделей

**Статусы выполнения:** [рабочий чек-лист](UNIFIED_CONNECTOR_CHECKLIST_RU.md).
Этот документ сохраняет архитектуру, принятые решения и историю проверок.

Дата начала: 01.10.2026. Основание: прямое поручение пользователя объединить
Structura Connector и Platform Connector в одно настольное приложение, начать
постепенно и перейти от повторной установки MSI к загрузке обновления и перезапуску.

## Принятое направление

Единый пользовательский продукт — Structura Connector. Основа оболочки и
дистрибутива — `connector-desktop` в `PROBIM55/ServerConnector`, рабочая ветка
`master`. Существующие функции Structura, VPN, Tekla, атрибутов и конвертера
сохраняются. Platform подключается модулем и использует существующие Core,
CAD adapters и Compute.Agr из `PROBIM55/platform`, без копии очереди заданий.

Первый пакет объединения — локальные исходники: вкладка Platform с подключением,
состоянием runtime и заданий; новая система пакетных обновлений; воспроизводимая
подготовка дистрибутива. Полный перенос инструментов Platform и переход рабочих
установок — следующие пакеты этого же плана. Это не завершенная миграция продукта.

На переходном этапе серверы и их авторизация сохраняют свои границы. Device token
Structura нельзя подставлять в Platform. Первый Platform-модуль использует свой
адрес API, свою DPAPI-защиту и прежний deviceId. Объединение интерфейса не дает
новых серверных прав. Это описание первого пакета, а не конечная схема подключения.

Дополнение пользователя от 01.10.2026 заменяет постоянную раздельную выдачу
доступов: целевая схема — один вход по токену, общий VPN по умолчанию и единый
центр управления в админке Platform. Пользователи, устройства, доступные модули
и общие папки управляются там. Раздельные доменные серверы могут сохраняться;
клиент получает их ограниченные учетные данные автоматически после регистрации.
Backend :8080, Platform production, Speckle production и текущие установки
в этом пакете не изменяются. Commit/push/публикация/деплой требуют отдельного поручения.

Дополнение пользователя: полный пересмотр UI/UX выделен в параллельное направление.
Сначала — предварительный UI-kit и несколько компоновок, затем выбор пользователя
и только после него перенос дизайна в WPF. Конвертеры становятся разделом общего
продукта: существующий FBX → GLB/ZIP, найденный IFC-оптимизатор и будущие форматы
используют единое ядро заданий, обновления и права. Отдельные очереди и оболочки
этих инструментов в новый Connector не переносятся.

Последующее решение пользователя: основа дизайна — темный Graphite; формы,
иконки и типографику доработать. В оболочке нужен явный переключатель
«Structura / Платформа», у каждого режима свои разделы и модули. Это заменяет
первоначальный общий список инструментов. Kit пересобирается, затем по нему
готовится полный интерфейс для согласования с настоящим составом страниц,
параметрами существующих модулей и действиями, а не только общими карточками.

01.10.2026 — пользователь согласовал новый знак Платформы и вернул работу к
основному объединению. Следом установил обязательную границу: весь код Connector
находится в одной директории и одном GitHub-репозитории. Канонический Git root —
`G:\00_Projects\18_Server`, `https://github.com/PROBIM55/ServerConnector`;
desktop/runtime/workers/tests — внутри `connector-desktop/`.
Это заменяет прежнее решение о выпуске общего SDK из отдельного репозитория
Platform и переходную сборку через `PlatformSourceRoot`. Все будущие изменения
компонентов Connector выполняются здесь; прежние проекты служат историей
переноса и действующими установками до приемки миграции, не источником сборки.
ConnectorAccess и web-пакет админки также разрабатываются в этом monorepo;
Платформа подключает опубликованные компоненты в свой существующий host.
Ее общие identity/roles и продуктовый host не дублируются в Connector.

## Инварианты объединения

1. Одна оболочка, один механизм обновления, один дистрибутив. Platform не создает
   дополнительный connector executable, свою запись автозапуска или свой updater.
2. Существующий Core Platform перенесен в единую кодовую базу и переиспользуется;
   адаптеры не создают вторую job queue, idempotency, bootstrap или heartbeat.
   Компиляция не зависит от соседнего checkout или абсолютного developer path.
3. На первом этапе Platform включается явно. Нет автоматического подключения,
   чтения токена или остановки работающего старого клиента при открытии вкладки.
4. Никакого принудительного закрытия Tekla, AutoCAD или действующего задания для
   установки обновления. Перезапуск откладывается при активной операции.
5. Настройки, журналы, DPAPI-токены и job state живут вне заменяемого каталога
   бинарников; автозапуск использует стабильный launcher управляемой установки.
6. Пакетный updater получает явно заданный HTTPS feed. В поставке нет приватного
   GitHub token и нет предположения, что новый production endpoint уже существует.
7. Версии NuGet updater и упаковщика vpk фиксируются совместно. Delta-пакеты
   строятся с предыдущими пакетами; при их отсутствии остается полный пакет.
8. Старый MSI updater остается только на время перехода существующих установок.
   После приемки миграции отдельный Platform desktop и повторная MSI-схема
   выводятся из эксплуатации; это не постоянные альтернативные продукты.
9. Рабочие сетевые подключения Structura и Platform используют общий VPN.
   Недоступность VPN блокирует защищенные сетевые операции; прямое подключение
   к публичному адресу API/SMB не служит скрытым обходом. Туннель сам по себе
   не заменяет авторизацию API и права на папки.
10. Первое подключение не требует внесения внешнего IP пользователя. IP —
    диагностический атрибут, права привязаны к пользователю и устройству.
11. Источник прав и управления устройствами — Platform. Скрытие вкладки,
    локальная настройка и заявленные клиентом capabilities не предоставляют
    доступ: разрешения проверяют серверы и SMB ACL.
12. Одна библиотека компонентов и источник design tokens. Рабочие модули не
    создают собственные темы, очередь, экран диагностики или механизм обновления.
13. Конвертер сохраняет исходник; результат публикуется отдельным артефактом
    после проверки. IFC с BIM-семантикой и GLB для визуализации имеют разные
    гарантии сохранности данных, которые указаны в профиле операции.
14. Переключение продуктового режима меняет навигацию и контекст представления,
    не запускает второй runtime, не переподключает устройство и не отменяет jobs.
    При создании задания фиксируются product/project/tenant; дальнейшее переключение
    экрана не меняет их. Выбранный режим сам по себе не предоставляет прав.

## Целевая архитектура и выбор технологий

Основание: поручение пользователя от 01.10.2026 — подготовить архитектуру под
развитие и параллельную реализацию, с исследованием существующего кода и технологий.
Ниже — проект решения; отметки выполненного относятся только к фактическим проверкам.

### Ядро и границы ответственности

Архитектура — модульный продукт с общим ядром и отдельными адаптерами.
Существующий `Platform.Connector.Core` становится источником общего runtime:
`ConnectorRuntimeHost`, supervisor/reconnect, worker, job runner и idempotency
уже реализованы. Их разделение и развитие сохраняют проверенные контракты.
Направление зависимостей: UI/адаптеры → application/core → domain/contracts;
core не зависит от WPF, DPAPI, конкретного HTTP-клиента или SDK Tekla.
Это применение [Clean Architecture](https://learn.microsoft.com/en-us/dotnet/standard/modern-web-apps-azure-architecture/common-web-application-architectures),
а не требование создавать по проекту на каждый небольшой класс.

| Компонент | За что отвечает | Чего в нем нет |
|---|---|---|
| Desktop WPF | Экраны, команды пользователя, состояние подключения/заданий | Управления очередью, VPN-процессами и ключами напрямую |
| Общий Agent + Core | Один lifecycle, подключения, права, очередь, расписание, повторы, безопасное обновление | Зависимостей от окна и загруженного Tekla SDK |
| Infrastructure | HTTP, локальное хранилище, процессы, секреты, Windows-интеграция | Решений о том, кому какие модули разрешены |
| Modules/workers | Structura Sync, Platform/CAD, AGR, IFC/Speckle; обработчики согласованных типов заданий | Собственных updater, device registration и второй общей очереди |
| Штатная служба NetBird и установщик с повышением прав | VPN-интерфейс, маршруты и однократная установка/обновление проверенного компонента | Выполнения произвольных команд, пользовательского CAD-кода и монтирования дисков для SYSTEM |
| Platform ConnectorAccess | Регистрация, пользователи/устройства, профиль прав, ресурсы, аудит и адаптеры выдачи доступа | Копии VPN-криптографии и отдельной пользовательской админки |

Фоновый Agent отделяется от WPF-процесса, работает в контексте пользователя и
продолжает задания при закрытом окне. UI и Agent входят в один дистрибутив,
один автозапуск и один механизм обновления; пользователю виден один Connector.
Этот целевой процессный контракт заменяет размещение runtime внутри окна U1;
первый пакет остается переходной композицией. В службе SYSTEM не запускаются
Tekla, AutoCAD, Blender и пользовательские плагины. Для экспорта без входа
пользователя — отдельный поддерживаемый режим того же Agent на выделенной машине
под выделенной учетной записью, после проверки лицензии и Windows session.

Общий SDK разрабатывается и выпускается из этого monorepo как версионированные
компоненты contracts, core и infrastructure. Desktop использует локальные
ProjectReference; NuGet нужен для опубликованных интеграций с другими host,
а не как способ разнести исходники Connector по репозиториям. Контракты DTO/IPC
совместимы с net48 worker, например через небольшой netstandard2.0 пакет и
версионированные JSON-схемы. `IProviderAdapter`/`IConnectorJobExecutor` сохраняются
или меняются через явную совместимую миграцию. Один checkout содержит исходники
всех компонентов; CI фиксирует commit этого репозитория и версии внешних библиотек.
Модули регистрируются через DI/каталог и поставляются согласованным подписанным
пакетом. Права на модуль и его техническая готовность — разные состояния.

### Стек и эксплуатация

- Desktop/Agent/Core и модуль доступа Platform — C#/.NET 10 LTS; WPF сохраняется
  для Windows/CAD. Сейчас установлен только SDK 8.0.422, переход еще не проверен.
  Поддержка .NET 8 заканчивается 10.11.2026, .NET 10 — 14.11.2028:
  [официальная таблица Microsoft](https://dotnet.microsoft.com/en-us/platform/support/policy).
  A0 включает матрицу совместимости зависимостей; net48 остается только внутри
  worker, которому он необходим по контракту Tekla/Speckle.
- Сервер доступа — изолированный модуль существующего ASP.NET Core Platform,
  с собственными domain/application/infrastructure границами и PostgreSQL-схемой.
  Существующие identity/роли переиспользуются после проверки серверных ограничений.
  Отдельный identity provider добавляется при реальной потребности SSO/MFA;
  текущую регистрацию устройств нельзя подменять еще одной общей таблицей паролей.
- На устройстве — локальная SQLite для состояния заданий, шагов, результатов,
  ожидающих отправки событий и версий схемы. Один Agent владеет записью; worker
  сообщает результат по IPC, UI получает snapshot. WAL используется только на
  локальном диске с явной политикой durability/backup: [SQLite WAL](https://www.sqlite.org/wal.html).
  Текущее файловое idempotency state мигрируется, не обнуляется.
- На сервере сохраняется общая система заданий Platform. Для масштабирования
  — устойчивые leases, идемпотентные операции и transactional outbox; при
  нескольких потребителях проверяется атомарное получение задания, например
  [PostgreSQL SKIP LOCKED](https://www.postgresql.org/docs/current/sql-select.html).
  Это целевые свойства существующей очереди, а не уже доказанные функции.
- IPC локальный, версионированный, с проверкой пользователя/SID и ACL. Для broker
  — только узкие команды и доверенные защищенные пути, без shell строк от клиента.
  Named pipes закрываются для сетевых пользователей; loopback не считается
  авторизацией: [Windows IPC](https://learn.microsoft.com/windows/win32/ipc/named-pipes).
- Диагностика — структурированные журналы и OpenTelemetry; сквозные deviceId,
  requestId, stepId, artifactId. Секреты исключены; админ видит причину отказа,
  ожидаемое и примененное состояние доступа, задержки и версию компонента.

### VPN: предпочтительный кандидат и обязательная проверка

Предпочтительный кандидат — self-hosted NetBird: готовый WireGuard overlay,
управление peers/groups/policies через API, Windows daemon и TCP 443 relay.
Platform управляет правами через серверный адаптер; пользователь не входит
в отдельную админку NetBird. Сначала N1 подтверждает пригодность на тестовом
контуре; текущий AmneziaWG сохраняется до принятой миграции.

NetBird **использует WireGuard для шифрованного туннеля**, а не заменяет его
другим криптографическим протоколом. Он выбран кандидатом ради готового
управления устройствами и сетевыми политиками, отзыва peer и резервного
relay через TCP/443. Сохранить только нынешний AmneziaWG возможно, но тогда
регистрацию/ротацию peer, разграничение сетевых ресурсов, аудит и relay придётся
создавать и сопровождать как собственный control plane. Цена выбора NetBird —
дополнительные серверные компоненты, Windows-служба, установка с повышением прав
и требование доказать точную связь device identity с peer. Это решение не
отменяет старый AmneziaWG для ещё не обновившихся пользователей и остаётся
условным до живого Windows/VPN/SMB PoC.

Документация подтверждает [Windows service/CLI](https://docs.netbird.io/get-started/cli),
[REST API](https://docs.netbird.io/api) и
[WebSocket relay на TCP 443](https://docs.netbird.io/selfhosted/selfhosted-guide).
Основной путь может использовать UDP; резервный — TCP 443. Прокси с запретом
WebSocket, TLS inspection, MTU и скорость SMB проверяются отдельно.
Подключение через relay должно измеряться передачей файла, а не только ping.

**Уточнение A2 от 02.10.2026 заменяет прежнее решение о собственной постоянно
работающей системной VPN-службе** в таблице компонентов и пакете 1C. NetBird
уже устанавливает штатную Windows-службу, которая владеет интерфейсом и маршрутами;
Connector не должен создавать её дубль. Привилегированный шаг нужен только для
первичной установки и обновления закреплённого поставщика. Для него проверяются
точный хеш установщика, подпись издателя и версия, а исполняемый CLI допускается
лишь из защищённого `Program Files`. Рабочий пользовательский Agent выполняет
ограниченные `up/status` через штатный daemon. В выбранной поставке отключаются
профили и изменение системных настроек; отдельный UI NetBird не запускается.
Версии ниже `0.76.0` запрещены из-за
[исправленной уязвимости локального IPC](https://github.com/netbirdio/netbird/security/advisories/GHSA-qcpp-8vwj-hhwr).
`NetBirdCliClient` допускает `up` только через подтверждённый ownership gate и
после чтения состояния daemon. Desktop runtime уже вызывает read-only gate с
закреплёнными путями машинного набора в `Program Files`; пока этот набор не
установлен, подключение закрыто. Точный peer readback ещё не выполнен,
поэтому клиент не считается готовым к рабочей сети.
Чужая служба не перенастраивается и не останавливается. Отдельный узкий broker
допустим лишь если закреплённый установщик не покрывает повышенные операции;
его локальный IPC должен проверять SID и запрещать сетевых клиентов и
произвольные команды согласно
[правилам безопасности named pipe](https://learn.microsoft.com/windows/win32/ipc/named-pipe-security-and-access-rights).

**Состояние A2 после локальной реализации 02.10.2026.** Закреплённый MSI и
read-only Windows preflight проверены на этом ПК; штатный NetBird здесь ещё не
установлен. CLI теперь закрывает `up` при неподтверждённом владельце или чужом
management URL, поэтому включение common-mode без установленного машинного
набора ожидаемо не подключится. Привилегированную установку нельзя строить запуском
PowerShell-скрипта или MSI из пользовательского каталога Velopack: этот каталог
доступен пользователю на запись между проверкой и UAC. Следующий пакет —
защищённый машинный bootstrap с повторной проверкой MSI после переноса в
закрытый каталог, фиксацией владельца и послестартовым readback. Конфигурация
enrollment/issuer pin также читается из защищённого машинного каталога, а не
из обновляемого профиля пользователя; локальный preflight выполняется до
отправки одноразового токена. Новый защищённый конфиг закрепляет HTTPS
`netBirdManagementUri`: чужое подключение отсекается до расходования токена.
Старый конфиг без этого поля остаётся пригодным для восстановления уже выданной
server-bound identity, но не для новой регистрации на зарегистрированном daemon.
Read-only assessment машинного пакета уже проверяет pinned MSI и конфиг, но
всегда возвращает `blocked-signed-launcher-required`: скрипт из каталога,
доступного пользователю на запись, не получает права установки через UAC.
Для installer нужен подписанный доверенный launcher и сценарий восстановления
при сбое после установки MSI, до записи owner-marker. Отдельно нужно доказать
связь локального `publicKey` с серверным `PeerId`: публичный
NetBird Peers API не предоставляет этот ключ, поэтому совпадение одного лишь
URI/IP не принимается как точная peer identity. Эти границы остаются открытыми
для контролируемого server-side решения: в NetBird `v0.79.0` ключ хранится
как `peer.Key` в [upstream server model](https://github.com/netbirdio/netbird/blob/v0.79.0/management/server/peer/peer.go),
но [REST response mapper](https://github.com/netbirdio/netbird/blob/v0.79.0/management/server/http/handlers/peers/peers_handler.go)
не включает его в `GET /api/peers/{peerId}`. Проверять связь надо через
поддержанный upstream API либо узкое серверное расширение для сервисной роли;
прямой доступ Connector к БД NetBird не закладывается.

Проверка [регистрации peer в NetBird `v0.79.0`](https://github.com/netbirdio/netbird/blob/v0.79.0/management/server/peer.go#L690-L727)
уточнила эту границу: `Peer.ID` создаётся отдельно от WireGuard `Peer.Key`,
поэтому вывести ключ из ID нельзя.
[Штатный daemon status](https://github.com/netbirdio/netbird/blob/v0.79.0/client/status/status.go)
содержит для видимых peer `netbirdIp`, `publicKey` и время последнего
WireGuard-handshake. Это кандидат на поддержанный серверный источник ключа
без форка management API. Его недостаточно отдельно от защищённого пути:
сервер должен принимать короткий mTLS-запрос непосредственно через NetBird,
сверять сертификат устройства, текущие `PeerId`/IP/права, источник соединения
на overlay-интерфейсе и свежую карту daemon, а перед удалением старых MSI
повторно подтверждать эту связку. Публичный reverse proxy, forwarded IP,
совпадение только адреса, stale/дублирующаяся запись daemon и смена peer
дают отказ. Нужны защита бинарника/сокета daemon, VPN-only firewall/listener
и живой двухклиентный тест; до них production peer-proof остаётся закрытым.
`connector-access` остаётся библиотекой; действующий Connector обслуживается
Python/Caddy, а публичный proxy ведёт на legacy API. В исходниках Platform-host
есть opt-in .NET listener на отдельном overlay-IP/порту с HTTPS/mTLS и отказом
private-маршруту на остальных сокетах. По умолчанию адрес ограничен
[диапазоном NetBird `100.64.0.0/10`](https://docs.netbird.io/manage/networks/masquerade);
для другого диапазона требуется явный безопасный CIDR. Host-адаптер сейчас
лежит в репозитории Платформы, поэтому требование единого исходного каталога
ещё не выполнено. Реальные NetBird-интерфейс, firewall, сертификаты и прямой
двухклиентный mTLS-сценарий не проверены; production-маршрут не включён.

Состояние одноразовых setup keys на сервере хранится через отдельный
постоянный Data Protection key-ring NetBird с RSA-шифрованием ключей. Он не
меняет глобальный provider Платформы или SMB. Каталог ключей, PFX и имя
переменной с паролем задаются серверной конфигурацией. Регистрация до запуска
отклоняет незашифрованный старый key-ring и ключи, которые нельзя расшифровать
текущим сертификатом. Файлы каталога и сертификат требуют серверных ACL;
ротация PFX должна сохранять возможность чтения старых ключей до миграции
состояния. Это проверено локальными тестами, но не на Windows production.

Отсутствие собственного сертификата подписи не запрещает изолированный
локальный тест с явным UAC и официально подписанным NetBird MSI. Такой тест
не является доверенным production-релизом: пользовательский Velopack-каталог
не должен становиться источником повышенного PowerShell/CLI, а выпуск для
пользователей остаётся закрыт до проверенного bootstrapper и подписи.
Проверена также стабильная `v0.80.0` и upstream `main` на 02.10.2026:
в [Peer OpenAPI schema](https://github.com/netbirdio/netbird/blob/v0.80.0/shared/management/http/api/openapi.yml)
ключа в ответе по-прежнему нет. Простое обновление NetBird этот контракт
не закрывает; версию VPN-клиента не поднимаем ради недоказанного эффекта до
живого Windows/NetBird теста.

Важные ограничения, которые нельзя скрывать:

- Свойство `AUTOSTART` зависит от конкретного MSI: прямое чтение таблицы
  `Property` закреплённого `v0.79.0` показало, что его там нет, хотя текущая
  [Windows-инструкция](https://docs.netbird.io/get-started/install/windows)
  описывает его для другой поставки. В проверенном MSI `NetBirdService` имеет
  `StartType=2`, запускается установщиком под `LocalSystem`. Управление tray UI
  проектируется отдельно; неподтверждённые MSI-свойства не передаются. MSI
  ставится с повышенными правами и обновляется тем же типом установщика.
- В [setup-key API](https://docs.netbird.io/api/resources/setup-keys) есть one-off
  и usage limit, но минимальный expires_in сейчас 86400 секунд. Поэтому короткий
  пользовательский enrollment — токен Platform; VPN-key создается только на его
  подтвержденной регистрации, имеет usage limit 1, ожидающий peer без ресурсных
  прав и принудительно отзывается при завершении/таймауте. Долгоживущие ключи
  не раздаются пользователям. Отзыв enrollment/setup key сам по себе не отзывает
  уже зарегистрированный peer: необходимы peer revoke и сервисные/SMB ограничения.
- Client-код NetBird — BSD-3-Clause, серверные management/signal/relay/combined —
  AGPLv3: [лицензия исходников](https://github.com/netbirdio/netbird/blob/main/LICENSE).
  Поставка учитывает NOTICE/SBOM и условия конкретного выбранного компонента.
  Private fork серверного движка не входит в архитектуру; интеграция через API.
- [Active-active HA Management/Signal](https://docs.netbird.io/selfhosted/maintenance/scaling/high-availability)
  требует коммерческий NetBird Enterprise. Community-версию нельзя превратить
  в HA запуском двух контейнеров. На старте допустим один control server с
  проверенным восстановлением и внешними relays; RTO/RPO фиксируются явно.
  Enterprise/managed provider и стоимость рассматриваются до обещания HA/SLA.

Tailscale managed — резервный кандидат при неподходящих ограничениях self-hosted
NetBird, с отдельной оценкой Windows-интеграции, цены и размещения control plane.
Headscale не выбирается целевым масштабируемым основанием: его
[официальный FAQ](https://headscale.net/stable/about/faq/) ограничивает scope
небольшими сетями и предупреждает о нагрузке от большого числа перемещающихся peers.
Собственная криптография, VPN-транспорт и fork для обхода ограничений HA не планируются.

### Идентичность, надежность и обновления

У пользователя один enrollment token; у устройства — отдельная идентичность.
Предпочтительный device-auth — локальный ключ и стандартный клиентский X.509
сертификат (mTLS), короткие серверные сессии и проверка актуальных grants.
Он не равен WireGuard-ключу. A0/N2 фиксируют выдачу по CSR, issuer/rotation,
защиту CA и отзыв; готовые TLS/PKI средства, без собственного протокола подписи.
При TLS termination gateway доверяет только проверенному каналу сертификата,
не произвольному forwarded header: [ASP.NET certificate authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/certauth?view=aspnetcore-10.0).
Публичный enrollment не требует mTLS первого устройства; renewal/recovery
не должны попадать в цикл «истек ключ → нужен VPN → ключ не обновить».

Состояние доступа — desired/applied с версией и подтверждением от VPN/SMB/API.
Команды применения и отзыва повторяемы; outbox хранит незавершенные операции.
При частичном сбое система показывает pending/error и закрывает расширение
прав; отзыв повторяется до подтвержденного результата. Серверные API проверяют
блокировку независимо от доступности VPN control plane. Допустимая задержка
отзыва измеряется; мгновенный полный отзыв при отказавшем шлюзе не обещается.

SMB-диски подключает пользовательский Agent, чтобы их видел Проводник/CAD.
Служба SYSTEM обслуживает VPN, а не создает диски в чужой Windows-сессии:
[особенности mapped drives и UAC](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/mapped-drives-not-available-from-elevated-command).
На одном ПК с несколькими пользователями VPN-доступ устройства не становится
правами всех пользователей: API identity и SMB учетные записи/ACL проверяются
отдельно. Для unattended worker применяются UNC и его собственная учетная запись.

Доставка заданий допускает повтор; отсутствие повторного результата достигается
идемпотентностью и сверкой, не обещанием exactly-once. Для Tekla: согласованный
snapshot → net48/x64 worker → IFC/native artifact → Speckle versionId.
Каждый шаг хранит статус и результат; неоднозначный ответ публикации сначала
сверяется по requestId, а не повторяется вслепую или выбирает «последнюю версию».
На CAD session/модель действует ограничение параллельности и lease.

Velopack сохраняется как доставщик пользовательского пакета: full/delta,
подписанные бинарники, доверенный feed, stable/preview и поэтапный rollout.
Он поддерживает [delta packages](https://docs.velopack.io/packaging/deltas) и
[code signing](https://docs.velopack.io/packaging/signing), но это не заменяет
проверку доверенного издателя/метаданных и совместимости Core/modules/broker.
SYSTEM не загружает бинарники из пользовательского writable-каталога.
Системный VPN/broker обновляется отдельным подписанным привилегированным шагом
того же UpdateCoordinator; Windows может запросить UAC. Обычное обновление
UI/Agent не требует полной переустановки системных компонентов.

Перед apply Agent перестает брать новые задания, сохраняет состояние,
завершает/откладывает активные операции и штатно закрывает свои workers/UI.
Текущий `App.xaml.cs` еще использует auto-apply по умолчанию. Нужно отключить
автоматическое применение при старте до общего drain: в документации есть
`SetAutoApplyOnStartup(false)`. Velopack может завершать процессы, удерживающие
каталог current; недренированное приложение нельзя передавать этому механизму:
[startup/apply](https://docs.velopack.io/integrating/overview),
[Windows update behavior](https://docs.velopack.io/packaging/operating-systems/windows).
Откат бинарников проверяется вместе с совместимостью миграций состояния;
необратимая миграция не объявляется автоматически откатываемой.

## VPN и подключение по одному токену

Целевой сценарий: администратор создает пользователя, назначает модули и папки,
выдает токен подключения. Пользователь устанавливает единый Connector, вводит
токен и нажимает «Подключиться». Приложение регистрирует устройство, получает
профиль доступа, поднимает VPN и подключает разрешенные сервисы и SMB-диски.
Адреса серверов и правила маршрутизации приходят из управляемого профиля.
Первичная установка VPN-компонента может потребовать штатное разрешение Windows;
это нужно отдельно проверить, не обещая отсутствие системного запроса.

Порядок регистрации и границы доступа:

1. До появления туннеля доступен узкий HTTPS endpoint регистрации на TCP 443.
   Он принимает токен из любой внешней сети без предварительного IP allowlist.
   Без успешной проверки токена он не выдает VPN-профиль, SMB-доступ или права
   API. Здесь нужны ограничения частоты/перебора и журнал без секретов.
   Bootstrap не должен требовать VPN, который сам же впервые создает.
2. Токен регистрации ограничен сроком, пользователем и числом устройств;
   по умолчанию одноразовый. Хранится на сервере как проверяемый хеш, показывается
   админу при выдаче. Повторный ввод использованного токена не создает новый peer;
   восстановление ответа после сетевого сбоя связано с той же регистрацией
   и доказательством владения ключом устройства.
3. Устройство получает стабильный идентификатор и собственный ключ, создаваемый
   локально. Закрытый ключ не отправляется на сервер; защита локального хранения
   учитывает учетную запись VPN-службы. Сервер связывает пользователя, устройство,
   открытый ключ, уникальный VPN peer и внутренний адрес. Изменение внешнего IP
   не требует новой выдачи прав или ручного firewall-правила.
4. После установления VPN выдаются сессии/учетные данные для разрешенных сервисов
   с ограниченными правами и сроком действия. Один пользовательский токен не
   подставляется в разные legacy API; совместимость обеспечивают серверные
   адаптеры выдачи доступа. VPN peer не получает административных полномочий.
5. Общий VPN lifecycle предшествует Platform runtime, сетевой синхронизации
   Structura и подключению SMB. Внутренние DNS/адреса, маршруты и проверка TLS
   согласуются для обоих продуктов. Доступ к Speckle при публикации включается
   в профиль явно, без предположения, что существующий public endpoint уже закрыт.
6. Отзыв устройства/пользователя закрывает новые API-операции и доступ к SMB,
   аннулирует сессии и peer; для уже открытых SMB-сеансов нужен отдельный механизм
   завершения. Политика отмены/безопасного завершения активного задания задается
   явно. Отзыв может ждать финализации только в пределах заданного времени.

Внешние точки входа фиксируются: HTTPS регистрации и согласованный транспорт VPN
на конкретном порту. Реальные порты API и SMB находятся внутри защищенной сети;
SMB 445 не открывается всему интернету. Маршруты выдаются только к необходимым
ресурсам; права разных пользователей изолируются на шлюзе/сервисах. Не считать
клиентский `AllowedIPs` достаточным ограничением доступа и не перенаправлять
весь интернет-трафик пользователя без отдельной необходимости.

В N1 нужно проверить нынешний VPN и выбрать транспорт/порт, включая сценарий
блокировки UDP. TCP 443 и UDP 443 — разные разрешения сети; одного номера порта
недостаточно, чтобы обещать доступность в любой сети. Требование — автоматический
проверенный резервный путь при блокировке основного транспорта и понятная
диагностика при полном запрете VPN, без открытия прикладных портов наружу.
HTTPS-загрузка установщика/подписанных обновлений может быть доступна до VPN;
это отдельный ограниченный канал доставки, который не дает прав на сервисы.

## Единая админка Platform и права модулей

В существующую админку Platform переносится управление Structura Connector,
а не только ссылка на его отдельную панель. Администратор видит пользователя,
его устройства, выданные доступы и состояние подключения в одном месте.
Административные действия используют существующую авторизацию Platform,
проверку роли и границ компании/проекта; device token не открывает админку.

Нужные возможности:

- Создать/заблокировать пользователя, назначить компанию/проекты и роль;
  выдать, отозвать и перевыпустить токен регистрации. Показать устройства,
  VPN/heartbeat, версию приложения и историю действий без вывода секретов.
- Назначить доступные модули и разделы: Platform, Structura, Tekla Sync,
  атрибуты, конвертер, общие папки, будущая публикация IFC/Speckle.
  Каталог различает установленную возможность, разрешение и готовность runtime.
  Новые модули не включаются пользователю автоматически с обновлением бинарников.
- Назначить общие папки: сервер, share/подпапка, компании/проекты, чтение/запись
  и монтирование SMB-диска. Проверять конфликт буквы диска и доступность пути;
  применять разрешения на SMB-сервере и уровне файловой системы. Скрытый пункт
  меню не защищает папку от прямого открытия UNC. Не выдавать всем общий пароль
  с правами ко всем папкам; учитывать срок и отзыв учетных данных.
- Управлять профилем подключения и назначенными ресурсами, видеть причины отказа;
  ротация и отзыв прав оставляют audit-запись с инициатором и результатом.
  Массовые административные действия требуют соответствующего серверного права.

Эффективные разрешения ограничены правами пользователя/проекта и устройства;
клиентские capabilities могут только сузить набор выполняемых операций.
Профиль имеет версию: heartbeat/переподключение обновляют вкладки, подключения
и задания; просроченная сессия не позволяет продолжать сетевую работу по старому
кешу прав. Для локальных операций явно задается отдельная offline-политика.
Проверки разрешений обязательны в API, выдаче заданий, загрузке/публикации
артефактов и SMB, включая прямой запрос вне интерфейса Connector.

Миграция сохраняет сопоставление существующих пользователей, deviceId, токенов,
VPN peers, папок и прав. Legacy-серверы на переходе управляются через ограниченные
серверные адаптеры Platform; у каждой сущности один владелец записи. Не переносить
старые привилегии по одному совпадению имени и не держать две независимые панели
редактирования одних прав после перехода. Старую админку выводить из эксплуатации
после проверки эквивалентности и сценария возврата. Изменения БД — миграциями
в соответствующих репозиториях; сетевые/prod изменения — отдельными пакетами.

Первый пакет U1 этого еще не реализует: ручное Platform-подключение с отдельным
токеном, текущий bootstrap и опциональный VPN остаются переходным состоянием.
Единый защищенный вход и централизованные права проверяются в N1–N7 до U8.

## Конвертеры: адаптеры существующих движков в общей очереди

Каталог конвертеров — часть каталога модулей A0, а не отдельный plugin manager.
Версионируемый descriptor задает входные/выходные форматы, профили и schema
параметров, поддерживаемые analyze/progress/cancel, worker/protocol version,
ресурсные ограничения, способ отмены (`cooperative`/`owned-process`/`none`) и
требования к разрешениям. Общий JobEnvelope передает
проверенные inputs/options; JobStepResult и ArtifactReceipt возвращают прогресс,
результаты, hashes и отчет. UI не формирует произвольную shell-команду.

Agent владеет очередью, SQLite state, повторами и lifecycle workers независимо
от открытого окна. FBX адаптер использует `Connector.AgrConversion`, не переписывая
парсер/геометрию. IFC адаптер запускает существующий `serve` engine через отдельный
локальный процесс на один job/attempt и переводит его NDJSON в общий контракт.
Его desktop UI, UI-очередь и updater не встраиваются. В существующем `serve`
нет работающей параллельной cancel-команды; её отправка в stdin не является отменой.
IFC adapter объявляет `owned-process`: Agent удерживает Windows Job Object
только для созданного им sidecar/потомков, при явной отмене пользователя завершает
их и дожидается выхода, фиксирует canceled attempt и очищает свой job workspace.
Output engine направлен в staging workspace, окончательную публикацию делает
Agent после receipt/validation. Commit результата и cancel сериализуются:
завершенное задание не превращается в отмененное, отмененный attempt не публикуется.
Для FBX native working directory отделён от staging результата: Windows не
запускает дочерний процесс при рабочем пути длиннее MAX_PATH. Рабочие файлы
создаются под локальным `%USERPROFILE%/.structura-connector/work/job-<id>`;
длина ограничена, владелец и защищённая ACL допускают только текущего пользователя,
SYSTEM и Administrators. Проверяются предки, корень тома и reparse points;
чужое право удалить/заменить каталог или изменить ACL блокирует запуск.
Очистка удаляет только каталог своего задания. Выбранная пользователем папка
результата сохраняется, включая длинные пути; ZIP и manifest публикуются
существующим атомарным переносом staging. Это уточняет прежнее общее правило
workspace, а не меняет формат AGR или реализацию IFC-оптимизатора.
Update drain ожидает завершения работ; таймаут блокирует apply и вызывает Resume,
а не принудительно отменяет IFC/CAD. Protocol handshake, отмена/гонка с результатом,
crash/restart и готовность к drain проверяются на реальном sidecar. Python и зависимости
поставляются закрепленным worker-пакетом через общий updater; пользователь не
устанавливает pip и отдельное приложение. Источник/commit и лицензии фиксируются
до упаковки; совпадения строки версии установленного exe недостаточно.

Ресурсный планировщик A0 ограничивает параллельность по памяти/CPU и типу worker;
тяжелые IFC по умолчанию обрабатываются последовательно, без второй IFC-очереди.
Файлы проверяются по типу/размеру, archive paths канонизируются, применяются квоты
на распаковку. Исходник read-only, временные результаты в отдельном job workspace;
успех фиксируется после проверки и атомарной публикации без перезаписи существующего
файла. Сбой/отмена не выдают частичный файл за готовый результат и не удаляют исходник.
Журнал отличает отмену пользователем от ошибки; повтор создает прослеживаемый attempt.

IFC-профиль `exact` — безопасный default без геометрического упрощения;
`compact` — явный выбор с описанием применяемых преобразований и отчетом.
Проверяем GUID, свойства, материалы/стили, единицы и мировые координаты,
геометрию и возможность повторного открытия. Число STEP-сущностей может уменьшаться:
его равенство не является критерием сохранности оптимизированного IFC.
Существующий engine проверяет semantic/representation/IFC/rendered geometry,
включая bbox/area/volume/orientation; неподдержанный mirrored map fail-closed
с `UNSUPPORTED_MIRRORED_MAP`. Эти исходные гарантии нужно повторно принять через
адаптер и пакет, а не считать доказанными чтением README. Для FBX → GLB критерии
другие: масштаб, расположение, материалы, визуальный результат и ZIP/manifest.

Локальная конвертация работает offline по явно заданной политике устройства;
срок действия cached grants и поведение отзыва фиксируются в A0/N5.
Защищенная отправка в Platform/Speckle/SMB требует общего VPN и серверных прав.
Формат задания поддерживает цепочку «IFC export → optional optimize → publish»,
с отдельными исходным и обработанным артефактами. Публикация сохраняет конкретный
versionId/receipt, без подстановки latest. Расписание и следующие форматы
добавляются через этот же контракт после приемки первого ручного сценария.

## Границы сборки

Решение первой ревизии с `PlatformSourceRoot` отменено прямым требованием
пользователя об одной кодовой базе. `Connector.Platform` теперь ссылается только
на локальные `src/` и `cad/`. AGR Python/manifest находятся в `runtime/`, IFC
engine — в `workers/ifc-optimizer/`, CAD geometry/contracts — в `shared/`.
Это перенос владения исходниками, а не постоянная синхронизация копий Core.
`source-provenance.json` хранит исходные commits и hashes исключительно для истории.
Упаковщик проверяет локальные source boundaries; чужой Git checkout не требуется.
Существующие установщики и приложения не изменяются до отдельной приемки перехода.

## Параллельное выполнение агентами

Один координатор отвечает за архитектурный контракт, интеграцию и этот план.
Одновременно работают до трех субагентов, не считая координатора. Ревьюер
занимает освободившийся слот; вложенных исполнителей нет. Таблица ниже —
распределение существующих этапов, не отдельный backlog.

Сначала A0 фиксирует версии API/IPC/SDK и смысл схем: DeviceEnrollment,
DeviceIdentity, AccessProfile, ModuleGrant, ResourceGrant, JobEnvelope,
JobStepResult, ArtifactReceipt, DrainState и ComponentCompatibility.
У схем один владелец; исполнители не правят их независимо. Converter descriptor,
option schemas и resource budget C0 входят в этот контракт, а не создают второй SDK.
После фиксации
контрактов runtime, backend и сеть разрабатываются параллельно с fixtures.
Fixture позволяет начать раньше, но не считается приемкой совместимости.

A0 также фиксирует `ModuleDescriptor`/контракт регистрации модуля и IPC-команды
`RequestDrain → Draining/Blocked → ReadyToApply`, `AbortDrain`, `Resume`.
1A реализует остановку получения заданий и завершение workers; 1C реализует
готовность/совместимость broker. 2B предоставляет свою регистрацию в
`connector-desktop/Connector.Platform/PlatformModuleRegistration.cs`;
2C реализует UpdateCoordinator в `connector-desktop/Connector.Updates/` и
использует только этот IPC. Владелец ядра возвращает composition root интегратору
после 1A; интегратор последовательно подключает регистрации 2B и Coordinator 2C,
меняет ранний startup и завершение UI/Agent. Apply разрешен после подтвержденного
ReadyToApply всех компонентов; ошибка/таймаут оставляют старую версию и Resume.
Частичное подтверждение готовности никогда не считается общим drain.

После 0D агент не занимает слот в ожидании D2. В волнах 1/2 уже три исполнителя:

Обычный ограниченный пакет — Terra/medium; поиск — Luna/medium; Reviewer —
Terra/high. A0/A1 и критичный device-auth/privileged IPC могут использовать
Sol/high или xhigh с записанной причиной архитектурного/безопасностного риска.
Каждое задание задает роль, модель/effort, конкретные пути, контракт результата,
тесты и запреты; один job не дольше 40 минут. Незавершенное возвращается
координатору с проверенным состоянием, а не продолжает работать без границ.

Приемка пакета: целевые тесты его владельца, независимое ревью, один проход
исправлений и проверка затронутого. Интеграционные тесты запускает один владелец,
чтобы агенты не дублировали нагрузку. Успешная компиляция/fixture/юнит-тест
не заменяет реальную Windows/VPN/SMB/CAD и Chrome-проверку админки.
Масштабирование проверяется по заранее заданным количествам peers/jobs,
частоте reconnect, размерам IFC и бюджету задержек; численные SLO/RTO/RPO
фиксируются в A0, до обещаний. ServerAccess масштабируется отдельно от relays
и CAD worker pools; Enterprise HA — отдельное эксплуатационное решение.

Первоначальный пакет ограничивался исследованием и HTML-preview. На 02.10.2026
нативный интерфейс, общий Agent и значительная часть Access уже реализованы
локально; фактические закрытые и открытые пункты приведены в рабочем чек-листе.
Установщик однократной замены, живой NetBird/SMB, подписанный выпуск и
production-переход по-прежнему требуют реализации и отдельной приёмки.

## Однократная замена MSI и постепенная миграция пользователей

**Решение пользователя от 02.10.2026 заменяет прежний ручной порядок выше:**
пользователь запускает один установщик, который заменяет старые Structura и
Platform Connector на этом ПК, переносит сохранённые настройки и устанавливает
нужный VPN-компонент. Два старых приложения на ПК после перехода не остаются.
Другие пользователи, которые пока не обновились, продолжают работать со
старыми Connector.

Существующий клиент 1.0.31 умеет только `msiUrl` и `msiexec`; URL нового
Velopack Setup.exe в старый manifest подставлять нельзя. Старые manifest,
`/connect/bootstrap`, `/heartbeat`, AmneziaWG-профили, SMB-учётные записи и
права сохраняются до завершения перехода всех пользователей; старые Platform
API и их клиентский контракт тоже сохраняются. Новый feed,
регистрация и API живут отдельно; серверные изменения additive и не удаляют
старые записи или ACL. Новый администратор видит версию/тип подключения и
не отзывает старое устройство при регистрации нового без явного действия.

Для смешанного парка разделение каналов — проверяемый контракт, а не только
разные ссылки в UI. Текущий legacy `/updates/latest.json` читает GitHub
`releases/latest`; прежний код при отсутствии `Connector.Desktop.Setup.msi`
выбирал любой MSI релиза. Поэтому unified выпуск должен иметь отдельные
tag/asset/feed, а legacy loader — принимать только точное имя старого MSI и
старый тег `vX.Y.Z`. Когда GitHub `latest` уже указывает на unified выпуск,
старый endpoint должен использовать локальный legacy manifest с закреплённым
точным MSI и хешем;
он не предлагает новому клиенту старый MSI и не предлагает старому клиенту
unified MSI. Legacy workflow не должен запускаться от тега нового канала.

| Состояние ПК | Приложение и сеть | Требование к серверу |
|---|---|---|
| Ещё не обновлён | Старые Structura/Platform Connector и AmneziaWG | Прежние API, VPN, SMB и права работают без изменения |
| Обновлён | Один unified Connector; NetBird ставится тем же установщиком | Новый mTLS/API/VPN-доступ работает; старые сервисы для других ПК остаются |
| Ошибка перехода | Установщик восстанавливает оба старых клиента и их состояние | Старые токены/права не отозваны из-за неудачной установки |

Установщик новой версии выполняет одну управляемую транзакцию:

Оркестратор перехода работает в контексте прежнего Windows-пользователя:
именно он читает DPAPI-состояние и переносит настройки. Повышенный машинный
этап ограничен закреплёнными машинными действиями: NetBird MSI и его
восстановление, подготовка защищённого Setup.exe, пустого пользовательского
stage и машинного журнала. Он не получает
пользовательские токены. Оба старых MSI удаляются в контексте прежнего
Windows-пользователя: живой Windows Installer показывает `UserUnmanaged` и
его SID для Structura 1.0.31 и Platform 1.2.1. Запись удаления Platform в
`HKLM32` сама по себе не означает машинный MSI-контекст.
Под «пользовательскими токенами» здесь понимаются токены доступа к Structura
и Платформе, а не Windows-токен администратора при UAC. Машинный этап может
работать с повышенным Windows-токеном, но обязан исполняться из проверенного
подписанного установщика с закреплёнными командами и не принимать секреты
приложения. Одного членства в группе Administrators недостаточно для
доказательства происхождения самого установщика.
Если UAC выполнен под другой учётной записью, пользовательская миграция не
переключается на её профиль; такой вариант проверяется отдельно и при
неопределённости прерывается до удаления старых приложений.

Уточнение решения 02.10.2026: прежняя композиция, исполнявшая весь переход
в одном повышенном процессе, остаётся fail-closed прототипом. `WindowsHost`
создаёт защищённый stage Setup и NetBird ещё до пользовательской транзакции;
при обычном UAC с чужими админскими данными он не сможет сохранить SID/DPAPI
исходного пользователя. Подписанный [WiX Burn bundle](https://docs.firegiant.com/wix/tools/burn/)
может быть носителем машинного MSI и обеспечивает проверку хешей payload,
но отдельная обёртка только NetBird MSI не выполняет поздний откат: текущий
`UpgradeOrchestrator` может запросить `remove/restore` после установки новой
программы и проверки доступа. Следующий кодовый пакет должен вынести
`prepare/apply/remove/restore/reconcile` машинной части, staging Setup.exe,
создание защищённого каталога снимка и машинный журнал за типизированную
доверенную границу с проверенным SID клиента и durable-квитанцией; процесс исходного
пользователя сохраняет настройки, DPAPI, токен, старые MSI и Velopack.
Компонент с повышенными правами не получает секреты приложения. Для Windows
[UAC с вводом чужих админских данных](https://learn.microsoft.com/en-us/windows/win32/msi/using-windows-installer-with-uac)
и [named-pipe IPC](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights)
понадобится отдельная проверка SID, ACL, запрета удалённых клиентов и живой
сценарий на стандартном пользователе. До этого старые приложения не удаляются.

Решение по направлению IPC от 02.10.2026: использовать **одноразовый
повышенный helper на время перехода**, запущенный исходным процессом через
Windows `ShellExecuteEx` с `runas` и сохранённым handle процесса, а не
постоянную службу второго коннектора. Исходный процесс создаёт локальный
одноразовый pipe с узкой ACL; после подключения helper он сверяет PID клиента
через документированный для server handle
[GetNamedPipeClientProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeclientprocessid)
с PID сохранённого процесса. Права администратора, доверенное происхождение
образа helper и закреплённые payload проверяются отдельно: совпадение PID
само по себе их не доказывает. Helper остаётся жив до commit/rollback и
сохраняет собственные машинные квитанции для восстановления после обрыва.
Пробный пакет проверки происхождения постоянно установленной службы не
включается в рабочую композицию: клиентский `GetNamedPipeServerProcessId`
оказался вне документированного контракта API и оставлен fail-closed. Это
решение уточняет прежний вариант доверенной машинной границы, но не означает
готовность установщика или выполненный UAC/OTS smoke.

Уточнение от 03.10.2026 к решению 02.10: проверка helper на стороне исходного
процесса подтверждает только **одну сторону** канала. Helper как клиент этого
pipe не может проверять PID исходного сервера через документированный
[GetNamedPipeServerProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid):
API требует handle, созданный `CreateNamedPipe`, тогда как клиент открывает
pipe через `CreateFile`. Поэтому диагностический `MachineSessionProbe` не
разрешает команды, а `ConnectTrustedClient` остаётся закрытым. Для рабочего
канала нужен второй pipe, созданный helper, и свежий одноразовый nonce:
исходный процесс сначала проверяет клиентский PID helper на своём pipe и
только затем передаёт nonce; helper на втором pipe проверяет PID и SID
исходного пользователя, после чего возвращает nonce именно проверенному
клиенту. Оба pipe одноразовые, с узкими ACL и `FILE_FLAG_FIRST_PIPE_INSTANCE`;
при смерти любого процесса сеанс закрывается без повторного подключения по
одному PID. Это связывает два канала, но само по себе не доказывает, что
второй клиент — установленный коннектор: helper также должен сверять
защищённое расположение, закреплённый образ/издателя клиента и допустимость
конкретной команды. SID, PID и имена pipe из аргументов запуска — подсказки
для проверки, не удостоверения. Без этой взаимной проверки машинные операции
остаются закрытыми. Уточнение заменяет прежнее подразумеваемое допущение,
будто одного parent-server pipe достаточно для передачи команд.

Для исходного пользовательского процесса требуется защищённый источник
закреплённого образа: одноразовый bootstrapper из общего установщика размещается
в `Program Files` с машинными ACL, запускается **без повышения прав** от имени
исходного пользователя и остаётся отдельным компонентом того же Connector,
а не вторым пользовательским приложением или постоянно работающей службой.
Он удерживает handle вызываемого процесса до завершения взаимной проверки;
helper проверяет его SID, путь и хеш по манифесту выпуска, закреплённому
в машинном payload. Текущая пользовательская установка в `LocalAppData` не
является таким источником доверия. Решение от 03.10.2026 заменяет прежнее
требование коммерческой Authenticode-подписи: используется внешняя
ECDSA P-256 подпись манифеста, закреплённый публичный ключ и точные
SHA-256/размеры. До защищённого размещения и проверки запуска по этому
контракту машинные команды остаются запрещены.

Уточнение от 03.10.2026 заменяет прежний порядок сборки с встраиванием
хеша bootstrapper в helper: это создавало цикл через общую сборку и не
давало воспроизводимого выпуска. Теперь schema v4 подписывает **три**
готовых образа — helper, автономный `Setup.exe` и original-user bootstrapper.
После независимой сборки подпись создаётся внешним ключом P-256, а общий
встроенный публичный ключ проверяет её перед машинными операциями. Schema v3
для старых манифестов остаётся совместимой, но не используется в новом
выпуске. Образ helper остаётся
в уже проверяемом машинном каталоге
`%ProgramData%\StructuraConnectorInstaller\Helper`; `Program Files` относится
к bootstrapper и установленному манифесту, а не к пути исполняемого helper.
Значения из
командной строки, пользовательских настроек и переменных окружения не могут
заменять этот манифест. Release pipeline обязан проверять подпись манифеста,
все закреплённые файлы и ACL до публикации единого пакета.
Единый вход — [WiX Burn](https://docs.firegiant.com/wix/tools/burn/):
первым идёт машинный MSI со staging, после границы отката —
[per-user ExePackage](https://docs.firegiant.com/wix/schema/wxs/exepackage/)
без аргументов, который проверяет закреплённый bootstrapper и запускает его
от исходного пользователя. Реальный UAC/OTS, повторный запуск и установленный
переход должны подтвердить это поведение; XML и Debug-сборка bridge их не
доказывают. Первый запуск самого EXE доверяет каналу доставки: встроенная
подпись манифеста начинает действовать только после запуска bridge и не
удостоверяет внешний EXE перед Windows. Без доверенной издательской подписи
невозможно гарантировать отсутствие [предупреждения SmartScreen](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
или запрета неподписанного кода политикой устройства; самоподписанный
сертификат этого не исправляет. Не выдавать P-256 подпись обновлений за
Windows Authenticode.
Первый [Velopack `Setup.exe`](https://docs.velopack.io/packaging/installer) содержит приложение автономно; последующие
`releases.*.json` и `.nupkg` — отдельный канал обновлений и не покрываются
этим машинным манифестом. Пока защищённый установленный пакет и его живой
smoke отсутствуют, локальные тесты не разрешают повышение прав.

1. До изменения машины проверяет точные MSI ProductCode/UpgradeCode обоих
   старых приложений, работающие задания, все корни пользовательского состояния,
   доступность новой серверной схемы и комплект для возврата к обоим MSI.
   Сохраняет проверяемую копию настроек и Platform backup без раскрытия
   DPAPI-секретов другому пользователю.
2. Вместе с новым приложением доставляет официальный закреплённый NetBird MSI.
   После повышения прав проверяет его подпись, хеш, версию и владельца службы;
   уже установленный чужой NetBird не перенастраивает. Установка VPN выполняется
   установщиком, а не пользователем через отдельный скрипт или кнопку.
3. Завершает принятые задания обоих старых процессов, подготавливает и
   проверяет новый клиент, активирует его параллельно старым установкам и
   сохраняет `%LocalAppData%/ConnectorAgentDesktop`
   и `%LocalAppData%/Platform/Connector` с backup. Первый запуск под тем же Windows-пользователем
   читает прежний DPAPI-токен, пути фирмы, Model Sharing, IFC patch, папки,
   автозапуск и прочие настройки, а также импортирует Platform settings/token;
   миграция не обнуляет неизвестные поля JSON.
4. Просит один новый регистрационный токен, выданный администратором Платформы,
   и проверяет фактический новый вход, права, VPN-маршрут, SMB и основные модули.
   До этого момента оба старых MSI остаются установленными. При неудаче новый
   клиент удаляется, а прежние настройки и приложения остаются рабочими.
5. После проверки нового доступа удаляет только два точно распознанных старых
   MSI и проверяет итоговое состояние. Если удаление или итоговая проверка
   не проходят, восстанавливает оба старых MSI/ярлыки/автозапуск и исходные
   настройки из защищённого комплекта отката. Только после успешной проверки
   снимает точный принадлежавший старому Connector туннель
   `AmneziaWGTunnel$structura-vpn`; посторонние VPN-
   службы не трогает. После успешной замены дальнейшие обновления идут через
   Velopack без повторной установки всего приложения или NetBird при каждом релизе.

Сохранение старого токена само по себе не регистрирует новое устройство в
NetBird/Platform: старый `device_id` не содержит доказанной связи с
`user_id`/`company_id` и правами Платформы. Поэтому текущий контракт перехода —
**один установщик и один ввод нового токена**, без IP-списков и отдельных шагов
установки VPN. Старые токены остаются в защищённом состоянии для отката и не
отзываются до подтверждения нового доступа. Если новый вход недоступен,
старые приложения не удаляются. Полностью без ввода токена можно перейти только
после отдельного подтверждённого администратором соответствия старого устройства
пользователю/компании и серверного обмена с проверкой CSR; этот путь не входит
в текущий переход и не должен угадывать права из старого токена.

Уже установленный Structura 1.0.31 прячет окно в tray по обычному Close и не
предоставляет migration IPC. Поэтому установщик не может обещать бесшумное
завершение его активной работы: он ждёт штатного выхода или переносит замену
на безопасный момент, показывает понятный статус и не применяет `taskkill` к
занятому процессу. Отдельный промежуточный MSI с управляемым drain возможен,
если потребуется полностью автоматическое закрытие старого процесса.

На время смешанного парка старый серверный путь остаётся рабочим. Публичный
SMB/445 нельзя закрывать целиком до проверки, что оставшиеся старые пользователи
достигают своей папки по VPN либо через действующий адресный allowlist. Новый
клиент использует отдельный VPN-маршрут; его SMB-права не должны открывать обход
через публичный legacy-путь. Если общий Windows SMB listener не позволяет это
гарантировать, нужен отдельный сетевой endpoint для нового контура.

Приёмка: старый клиент на ПК A работает до и после обновления ПК B; на ПК B
после одного установщика работает только новый клиент с прежними данными;
ошибка на любом этапе восстанавливает старый клиент; отзыв нового устройства
не затрагивает старое. Окончательное отключение старых API/VPN/SMB и публичного
пути — отдельный этап после учёта и миграции последних старых клиентов.
Реальный переход и откат ещё не отрепетированы; выпуск пока закрыт U5/U6.

02.10.2026 — реализованы устойчивое локальное исполнение и протокол регистрации.
Это развивает принятые выше A1/N2/desired-applied решения, не заменяя общий kit.
Queue и Running сохраняются до исполнения; Running после сбоя получает Interrupted
без автоматического повторения. Один runtime-root удерживает OS file lease до
завершения consumer; новый экземпляр продолжает работу только после освобождения.
GUID локальной очереди связан с компьютером / Windows-пользователем через DPAPI.
SMB-запись фиксирует назначенный target, но не доказывает поколение подключения
Windows: удаление текущего selected drive требует подтверждения и повторной
сверки UNC; другие подключения не отключаются.

Регистрация находится в `connector-access`: постоянный pending CSR и тот же ключ
позволяют восстановить потерянный ответ или повторить issuer без второго устройства.
Короткий self-issued TLS cert разрешён только как доказательство для POST resume;
GET receipt и профиль требуют выданной идентичности. TLS policy отдельно фильтрует
issuer / bootstrap candidates; pass handshake не означает допуск к API.
Windows-клиент хранит private key в DPAPI, проверяет заранее заданный issuer pin
и не сохраняет enrollment token. Provider outbox фиксирует revision/action,
сериализует dispatch по device/provider и требует внешнего монотонного fence;
старая выдача прав после revoke отвергается, ошибка повторяется с backoff.
Практическое подключение к существующему Platform host описано в
[`connector-access/README_RU.md`](../../connector-access/README_RU.md).
Это локальная реализация протокола; live Platform/VPN/SMB-интеграция ещё открыта.
